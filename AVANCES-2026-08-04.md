### El componente: dos modos, dos criterios de corte

**`mode="clamp"`** (default) — trunca a N líneas con `line-clamp`. El botón
aparece sólo si el texto realmente se desborda, lo decide el JS midiendo
`scrollHeight` vs `clientHeight` después de `document.fonts.ready`. Se usa
en Producción Destacada, donde la descripción es un bloque corrido.

**`mode="paragraph"`** — muestra el primer párrafo y esconde el resto. El
corte se decide en el build (¿hay más de un párrafo?), no en el navegador:
no mide nada, no espera fuentes, no hay reflow. Parser tolerante a `\n` y
`\n\n` como separador. Con un solo párrafo no se renderiza botón.

Por qué el modo párrafo para hero y pilares: una línea renderizada no es una
unidad de contenido. La medición lo mostró — el pilar Consciencia ocupa 42
líneas a 1440px y 133 a 768px. Un clamp de 4 líneas cae en un lugar distinto
en cada pantalla, casi siempre a mitad de frase. El párrafo cae siempre en
el mismo lugar, elegido por quien escribe.

### Lecciones de proceso — las tres del día

**1. Un mensaje de commit en un pedido no es un `git add`.**
Dos rondas completas de trabajo (Fase 2 + sus correcciones), con
verificación y screenshots, quedaron viviendo **sólo en el working tree**.
Los pedidos terminaban en un bloque "COMMIT" que traía sólo el texto del
mensaje, sin comandos ejecutables. Se descubrió recién al pedir `git status`
antes del push: cero commits sobre origin/main.
El riesgo real: un `git checkout .` sin path se llevaba todo. Estuvo cerca —
en la verificación se editó y revirtió un `.yaml` con `git checkout --`.
**Regla nueva:** todo pedido que deba terminar en commit incluye los comandos
`git add` (con paths explícitos, nunca `git add .`) y `git commit`. Y un
`git status` pegado crudo antes de commitear.

**2. Una prueba en verde sobre una branch vacía no prueba nada.**
El plan incluía clonar la branch en limpio y correr `npm run build` para
simular Vercel. Si se hubiera ejecutado antes de descubrir lo anterior,
**habría pasado** — porque la branch clonada no tenía ni `ReadMore.astro` ni
el import que lo llama. Un sitio idéntico al del día anterior, compilando
perfecto. La prueba del clon limpio sólo vale después de confirmar que el
commit contiene lo que debe contener.

**3. El criterio del diff se enuncia sobre HTML y comportamiento, no sobre
líneas.**
El pedido decía "cualquier diferencia además de la línea del `<link>` es un
ERROR". En Fase 2b, `HeroSection.astro` importa `ReadMore` de forma
incondicional y Astro empaqueta el `<style>` scoped del componente importado
en toda página que use `HeroSection` — aunque esa rama del template no
renderice. Institucional, Proyectos y Archivo pasaron a tener 4 líneas de
diff en vez de 2: **CSS inerte, sin ningún elemento del DOM que lo matchee**
(verificado: 0 botones, 0 divs reales, mismo conteo de `<script>`).
Aceptado. Evitarlo requeriría import dinámico o partir el componente, que
cuesta más que el problema. La formulación por líneas era un proxy más
estricto que la intención.

### Los tres bugs de EpisodeList — una sola causa
Al pedir el relevamiento del badge "// reproduciendo" aparecieron tres, todos
del mismo origen: **el estado activo se fijaba en build time y el script sólo
actualizaba algunos elementos a mano.**

1. **Badge "// reproduciendo" congelado.** El `<span>` estaba dentro de
   `{ep.active && (...)}`, que Astro evalúa en el build. El script sólo hacía
   `classList.replace` sobre `.ep-num` y `.ep-title`. En proyectos sin
   adelanto el badge quedaba pegado al episodio 1; en proyectos **con**
   adelanto no aparecía nunca, porque ningún episodio tenía `active: true`.
2. **El `<h3>` del trailer nunca recuperaba el color.** Sin una clase que el
   script pudiera referenciar, al volver al trailer el fondo y el borde se
   movían pero el título no.
3. **Ningún ítem era accesible por teclado.** `<div>` con
   `addEventListener('click')`: sin `tabindex`, sin `role`, sin Enter ni
   Espacio, sin `aria-current`. **La lista de episodios estuvo cerrada al uso
   sin mouse desde siempre**, y nadie lo había notado.

**Solución: `aria-current` como fuente única de estado.** El script mueve un
único atributo; el CSS deriva todos los estados visuales. Antes, cada
elemento que debía reaccionar al estado activo tenía que ser tocado a mano
desde el script, y los que se olvidaban quedaban congelados — el badge y el
`<h3>` eran exactamente eso. Ahora un elemento nuevo sólo necesita una regla
CSS. Y `aria-current` **es** el estado accesible: el badge visual deja de ser
la única señal.

El badge ahora se renderiza en todos los ítems con `display: none`, que lo
saca también del árbol de accesibilidad — un lector de pantalla no lo lee N
veces. Agregados `role="button"`, `tabindex="0"`, Enter/Espacio y
`focus-visible`.

Este bug es el **punto ciego del método de verificación**, ya anticipado el
03/08: *"el diff compara HTML generado, no ejecuta JavaScript de cliente.
EpisodeList necesita clicks reales"*. El bug sólo existía después de un
click. Ninguna verificación lo ejecutaba hasta que los clicks se empezaron a
pedir explícitamente en los checks de sanidad.

### Lección de instrumentación
Verificando el color del `<h3>` del trailer, las lecturas por
`getComputedStyle()` dieron resultados contradictorios, incluido un
imposible: un `color: red !important` inline que no se reflejaba en la
lectura. Se cruzó contra capturas y clicks genuinos (no eventos sintéticos),
que mostraron el comportamiento correcto.

**Regla:** en `EpisodeList` las verificaciones de estado visual se hacen con
clicks reales y captura, no con lecturas de estilos vía JS. Ante una lectura
imposible, desconfiar del instrumento antes que del código.

### Regla nueva de proceso: commit ANTES de las pruebas destructivas
Verificando el fallback de los campos nuevos de `EpisodeList` se vaciaron los
3 campos del YAML y se revirtió con `git checkout -- <archivo>`. El comando
restauró a HEAD — que no tenía nada de esa sesión commiteado — y **se llevó
puesto el trabajo entero del paso 1**, no sólo la edición temporal. Se
detectó, se repuso y se re-verificó desde cero.

Es la **segunda vez en dos días** con el mismo patrón: trabajo sin commitear
+ un `git checkout --` de prueba. La causa raíz es de diseño de los pedidos:
el commit iba al final, después de las verificaciones.

**Regla:** toda prueba que modifique archivos para después revertirla se hace
sobre trabajo ya commiteado. Los pedidos ponen el commit **antes** de las
verificaciones destructivas. Si un pedido llega con el orden invertido, Code
avisa antes de ejecutar. Aplicada desde el PR #25 en adelante, y ya probada:
el `git checkout --` de Institucional fue seguro.
